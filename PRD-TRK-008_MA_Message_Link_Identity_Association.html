PRD-TRK-008
MA Message Link Identity Association

建立统一的 MA 消息链接 Identity Association 机制，支持 anonymous_id 与 MA Message User 的关联、MA Attribution 追踪与完整用户行为链路分析。 Unified identity association mechanism for MA message links, connecting anonymous visitors to known MA recipients.

01

Background 背景

MA 消息发送后，用户通过链接访问网站时，系统无法将访问行为与 MA Message User 关联，导致 Attribution 链路断裂。
核心问题 当前系统缺少 MA Link Identity Resolution 机制。anonymous_id 与 MA Message User 之间没有统一的关联路径，无法分析哪个 Flow、哪个 Node、哪个用户带来了访问与转化，也无法建立完整的 MA → Web → Conversion 行为链路。
Pain Point当前痛点
No stable MA link visitor identification无法稳定识别 MA 消息访问用户
No flow / node / user conversion attribution无法准确分析哪个 Flow / Node / 用户带来转化
anonymous_id and MA User identity not linkedanonymous_id 与 MA User Identity 缺乏统一关联机制
Incomplete MA → Web → Conversion journey无法建立完整 MA → Web → Conversion 行为链路

Core Principles 核心原则

#Principle原则说明
P1 anonymous_id is the system's sole anonymous identity
anonymous_id must equal GA4 client_id at all times, consistent with PRD-TRK-006.		 anonymous_id 必须等于 GA4 client_id，与 PRD-TRK-006 保持一致
P2 Identity stitching is Backend responsibility
Frontend must not resolve identity relationships, determine active identity, or execute stitching logic.		 Frontend 禁止解析 identity 关系、决定 active identity 或执行 stitching 逻辑
P3 MA Link identity ≠ active website identity
The identity in ma_ref represents the message recipient — not necessarily the current active website user.		 ma_ref 中的 identity 代表消息接收者，不一定等于当前网站 active identity

Backend Responsibilities Backend 职责

6.1 Resolve ma_ref
Responsibility说明
Verify JWT signature → extract payload (identity_token + attribution)验证 JWT 签名，提取 payload 中的 identity_token 和归因信息
Lookup Redis: ma_token:{token} → profile_id / v2_uid / flow / node / channel查询 Redis 获取 identity 与归因信息
Validate token TTL — return ma_ref_expired: true if expired校验 token 是否过期，过期时返回 expired 标志
Determine current active identity from session / auth token / cookie基于 session / auth token / cookie 判断当前 active identity
Execute identity association logic (Case A / B / C)执行 identity association 逻辑
Write to identity_association_current and identity_association_event_log写入两张数据表
JWT verification is the first step of every resolve-ma-ref call. Backend must verify the JWT HS256 signature before any identity lookup. Requests with invalid signatures are rejected immediately with ma_ref_invalid: true — no Redis lookup is performed. See PRD-TRK-007 Section 5.3 for the full JWT specification.
Frontend must NOT transmit active uid to Backend. Active identity determination is exclusively Backend responsibility based on server-side session state.

Identity Association Rules Identity 关联规则

7.1 Case A — No existing association
ASSOCIATED anonymous_id has no prior association
Condition: anonymous_id → null (no existing record in identity_association_current)
Action: Create new association: anonymous_id → profile_id from ma_ref
Result: association_status = associated
7.2 Case B — Same identity already associated
MATCHED anonymous_id already linked to same identity
Condition: anonymous_id → P123 AND ma_ref resolves to P123
Action: Update last_seen_at; record MA attribution event in event log
Result: association_status = matched
7.3 Case C — Conflict: different identity already associated
CONFLICT anonymous_id linked to a different identity
Condition: anonymous_id → U999 AND ma_ref resolves to P123
Action: Do NOT overwrite existing identity; record attribution_identity (P123) in event log; set identity_conflict = true
Result: association_status = conflict

Downstream behavior:
— MA attribution event is still recorded (flow / node attribution unaffected)
— Audience Gallery: exclude rows where identity_conflict = true
— Journey Analysis: use anonymous_id as primary key (conflict only affects user dimension)
— Conflict resolution: append a conflict_resolved event log entry after login (append-only, original record not modified)
CaseConditionActionassociation_status说明
ANo prior associationCreate new associationassociated首次关联，建立记录
BSame identity already linkedUpdate last_seen_at + log eventmatched已关联相同 identity，更新时间
CDifferent identity already linkedNo overwrite + conflict flagconflict冲突，不覆盖，记录冲突

Login Re-association Flow 登录后 Re-association

When an anonymous MA visitor logs in during the same GA4 session, Backend upgrades the identity association.
触发机制 由 PRD-TRK-006 Flow 3 的 login event 驱动。Frontend push login event 后，Backend 在处理登录时检查当前 session 内是否有 pending MA association 记录，并执行相应升级逻辑。
ScenarioAction说明
association_status = associated in current session Upgrade: anonymous_id → hashed_uid; update primary_identity_type = v2_uid; set association_source = MA+Login 将 anonymous_id → profile_id 的关联升级为 anonymous_id → hashed_uid
association_status = conflict in current session hashed_uid becomes authoritative identity; append conflict_resolved event log entry (do not modify original record) 登录后 hashed_uid 成为权威 identity，以 append-only 方式记录 conflict 消解
Scope boundary: Re-association only applies within the same GA4 session window. If the GA4 session has expired (30-min timeout) before login, re-association is not triggered. Cross-session identity stitching is handled by the Backend Identity Graph and is out of scope for this PRD.
Relationship to PRD-TRK-006 Identity Graph: identity_association_current is a lightweight, MA-attribution-scoped table — it does not replace or duplicate the general anonymous_id ↔ hashed_uid stitching performed by the Backend Identity Layer. As of PRD-TRK-006 v1.4, that general stitching has its own concrete raw storage table — login_identity_raw_log (PRD-TRK-006 Section 2.3.1/2.3.2), populated on every successful login, primary key anonymous_id, no uniqueness constraint on hashed_uid (supports multi-device). The Identity Graph remains the authoritative source for final identity resolution once built on top of that table; identity_association_current only tracks which MA flow/node/channel a given association originated from for attribution reporting — it is not a substitute for login_identity_raw_log.
说明：identity_association_current 是 MA 归因维度的轻量表，不替代、不重复 Backend Identity Layer 做的通用 anonymous_id ↔ hashed_uid stitching。截至 PRD-TRK-006 v1.4，通用 stitching 已经有自己的具体落地表 —— login_identity_raw_log（PRD-TRK-006 Section 2.3.1/2.3.2），在每次登录成功时写入，主键为 anonymous_id，hashed_uid 不加唯一约束（支持多设备）。最终身份判定仍以建立在这张表之上的 Identity Graph 为权威来源；identity_association_current 只负责记录这次关联来自哪个 MA flow/node/channel，用于归因报表，不能替代 login_identity_raw_log。
TableDefined inWritten when触发时机
login_identity_raw_logPRD-TRK-006 §2.3.1/2.3.2Every successful login每次登录成功
ma_ref_raw_logPRD-TRK-008 §9Every page load where ma_ref is present in URL (regardless of resolve success)URL 含 ma_ref 时,无论 resolve 是否成功
identity_association_currentPRD-TRK-008 §10.1Successful resolve-ma-ref (Case A/B/C) or Login Re-association (this section)resolve-ma-ref 成功，或本节的 Login Re-association
These three tables serve different trigger scenarios and do not overwrite or contradict each other. They converge on the same hashed_uid value once a user logs in — identity_association_current's primary_identity_id is upgraded to match what login_identity_raw_log already recorded for that anonymous_id.
Known limitation — shared device (see PRD-TRK-006 Section 8.1): Since identity_association_current stores one record per anonymous_id, the same shared-device limitation documented in PRD-TRK-006 applies here: if a device is used by different real users across different sessions, this table's record is overwritten by the most recent login rather than isolated per session. This PRD does not duplicate that explanation — refer to PRD-TRK-006 Section 8.1 for the full rationale and accepted-risk decision. The same decision (not engineering session-scoped binding in v1.0, low-frequency scenario) applies to this table.

Pre-launch Raw Capture 上线前原始数据捕获

PRD-TRK-006 (Tracking Context Initialization) typically ships before the full Identity Stitching logic in this PRD (Section 6–8) is complete. This section defines a minimal, decoupled capture mechanism so that ma_ref click data is never permanently lost during that gap.
为什么需要这一节 006（Tracking Context Initialization）通常会比本 PRD 完整的 Identity Stitching 逻辑（Section 6–8：JWT 验签、Redis 查询、Case A/B/C 判定）先上线。如果用户在这个窗口期点击了 MA 链接，resolve-ma-ref 调用会因为后端逻辑未就位而失败。ma_ref token 本身有 30 天有效期（JWT exp），一旦超过这个窗口才补开发，数据就永久丢失。本节定义一个不依赖完整业务逻辑的最小化捕获机制，解耦"存储原始数据"与"执行身份判定"这两个动作。
核心原则：存储 ≠ 执行 Stitching。 Storing a raw ma_ref requires zero business logic — no JWT verification, no Redis lookup, no Case A/B/C judgment. It is a plain INSERT. Executing Identity Stitching requires the full logic in Section 6–8. These two responsibilities are deliberately decoupled so the storage endpoint can ship independently of — and earlier than — the full Identity Stitching system.
9.1 Raw Capture Endpoint 最小化存储接口
A minimal endpoint that performs no parsing, no verification, and no identity logic — it only persists the raw fields it receives.
PropertySpecification规范说明
EndpointPOST /tracking/log-ma-ref-raw独立于 resolve-ma-ref 的极简接口
LogicNone — a single INSERT into ma_ref_raw_log. No JWT verification, no Redis lookup, no Case A/B/C evaluation无业务逻辑，仅一次 INSERT，不验证 JWT，不查 Redis，不判断 Case
DependencyNone on Section 6–8 — can be developed and shipped independently, even before Redis / JWT signing infrastructure exists不依赖 Section 6-8 任何逻辑，可独立开发上线，甚至可以在 Redis / JWT 签发体系搭建之前先上线
Failure modeIf this endpoint is also unavailable (e.g. before any Backend exists), Frontend silently skips — same fallback behavior as the full resolve-ma-ref call若此接口也不可用，前端静默跳过，降级行为与 resolve-ma-ref 一致
HTTPPOST /tracking/log-ma-ref-raw — Request (fire alongside resolve-ma-ref, independent of its result)
// Called unconditionally whenever ma_ref is present in the URL —
// regardless of whether resolve-ma-ref succeeds, fails, or the endpoint doesn't exist yet
{
  "ma_ref":       "abcxyz123",   // raw token, not parsed
  "anonymous_id": "<GA4 client_id>",
  "session_id":   "<GA4 ga_session_id>",
  "page_url":     "https://www.welovesupermom.com/campaign/123?ma_ref=abcxyz123"
}
Frontend implementation note: This call is fired in parallel with (not instead of) the full resolve-ma-ref call from Section 5. It does not block or depend on that call's outcome — it is a pure write-and-forget safety net.

9.3 Reconciliation on Full Launch 完整功能上线后的回扫处理
Once Section 6–8's full Identity Stitching logic is live, a one-time (or periodic, until backlog clears) batch job reconciles every unprocessed row.
StepAction说明
1Query ma_ref_raw_log WHERE processed = false查询所有未处理记录
2For each row, run it through the full Section 6 logic: JWT signature verification → Redis lookup → Case A/B/C evaluation逐条跑完整的 Section 6 逻辑：JWT 验签 → Redis 查询 → Case A/B/C 判定
3Write result to identity_association_current / identity_association_event_log as normal正常写入 identity_association_current / event_log
4Mark row as processed = true, set processed_at标记已处理
Time-sensitive — JWT exp window: Reconciliation only succeeds for rows where the ma_ref JWT has not yet expired (30-day exp, per Section 6.2 Token Security Spec) and the corresponding Redis entry has not been evicted. The full Identity Stitching system (Section 6–8) must go live within this 30-day window relative to the earliest captured row, or that row's identity resolution is permanently lost — only the raw ma_ref string remains, with no way to re-derive the identity it pointed to.
⚠ 时间敏感：回扫处理只能在 ma_ref 的 JWT 未过期（30 天 exp）且 Redis 记录未被清理的情况下成功。完整的 Identity Stitching 系统（Section 6-8）必须在最早一条捕获记录的 30 天窗口内上线，否则这条记录的身份解析将永久丢失——只剩下原始 ma_ref 字符串，无法再还原出它指向的身份。

API Contract 接口规范

HTTPPOST /tracking/resolve-ma-ref — Request Body
{
  "ma_ref":       "abcxyz123",         // required
  "anonymous_id": "GA4_client_id",     // required — undefined if GA4 unavailable
  "session_id":   "GA4_session_id",    // required — undefined if GA4 unavailable
  "page_url":     "https://..."        // required
}
JSONPOST /tracking/resolve-ma-ref — Response
{
  "association_status":     "matched",    // associated | matched | conflict
  "identity_conflict":      false,
  "resolved_identity_type": "profile_id", // profile_id | v2_uid | null (if expired)
  "ma_flow_id":             "FLOW_001",
  "ma_node_id":             "NODE_003",
  "ma_channel":             "email",      // email | whatsapp
  "ma_ref_expired":         false,
  "ma_ref_invalid":         false   // true when JWT signature verification fails
}
Frontend uses the response fields to construct the ma_identity_associated dataLayer event. No identity values (profile_id / v2_uid) are exposed to Frontend in this response.

Glossary

TermDefinition中文释义
ma_refThe opaque URL parameter appended to all MA message links. A JWT HS256 signed token carrying identity_token + flow + node + channel + exp. Tamper-proof — invalid signatures are rejected by Backend.MA 消息链接中的 JWT HS256 签名 token，包含 identity_token、归因信息和过期时间戳
identity_tokenA UUID v4 token stored in Redis at send time, referenced inside the JWT payload. Backend uses it to lookup profile_id / v2_uid via Redis. Contains no raw identity.发送时写入 Redis 的 UUID token，用于 lookup 真实 identity
association_statusResult of the identity association attempt. Enum: associated / matched / conflict / conflict_resolved.identity association 的结果状态
attribution_identityThe identity resolved from ma_ref (message recipient). May differ from the current active website identity.ma_ref 解析出的 identity，代表消息接收者，不一定等于当前 active identity
conflict_resolvedEvent log status appended when a Case C conflict is resolved after login. Original conflict record is never modified (append-only).Case C 冲突在登录后消解时追加的 event log 状态，原记录不修改
MA+Loginassociation_source value indicating the association was initially created via MA link and later upgraded upon login within the same session.MA 访问 + 同 session 登录后触发 re-association 的 association_source 值
re-associationThe process of upgrading an anonymous_id → profile_id association to anonymous_id → hashed_uid upon login within the same GA4 session.同 session 内登录后将 association 从 profile_id 升级为 hashed_uid 的过程
