1.看不懂字段名？先看这里

下文会反复出现 sm_media / utm_source / utm_medium / oldChannel 这几个名字，它们都不是同一个东西。先用一句话讲清楚每个是什么：

名字 它是什么（业务语言） 谁来决定它的值
media 系统最终要打在这条记录上的"渠道标签"——也就是本文档要讨论的结果，决定这条用户数据被归到 WhatsApp / 邮件 / 网站 / 通用 哪一类。这个值会通过 API 推送给 BOI（BeautyOne）各品牌方，本文档讨论的就是推送给每个品牌前，这个值是怎么算出来的 由下面几项共同决定，不是用户直接填的
sm_media 我们自己内部的来源参数，是否携带可以自主选择——不是系统强制自动带的。如果传了值，优先级最高，最先被检查 由提交方（内部业务/接口调用方）决定是否传、传什么
utm_source 用户点击的链接里自带的"来源"标记，例如这条链接是从 Facebook 广告来的还是从 EDM 邮件来的。日常说的"UTM 参数"就是它 市场/投放同学在做链接时配置的
utm_medium 和 utm_source 同一批 UTM 参数里的另一个字段，专门标"媒介类型"（比如 email、social、cpc）。它和上面的 media 是两个完全不同的字段，只是名字像 市场/投放同学在做链接时配置的
oldChannel 一个字段，目前代码中能看到的取值包括 #sleekflow / #EDM / #social* / #blog / #community / #CDPBanner。在判断顺序里优先级最低，只有前面几项都没有值时才会用到它。它具体代表什么、从哪里来，待业务确认 待业务确认具体来源

下文说的"优先级 1 / 2 / 3"，可以理解成：系统按顺序检查这几项有没有值，先看 sm_media，没有就看 utm_source，还没有就看 oldChannel，全都没有就用一个固定的默认值。就像填表时先看第一栏有没有填，没填看第二栏，依此类推。

4.标准三级优先级逻辑是什么

DORRA_SG、LondonWeight、NYSS_SG 三个 API 共用同一套判断顺序。理解了这一套，就理解了这三个 API 的核心逻辑——第 5 节里这三个 API 的卡片会直接引用这里，不再重复列步骤。

优先级 1
sm_media
  • 值为 supermom（不分大小写）→ 判定为 WHATSAPP-SUPERMOM
  • 其他非空值 → 原值直接透传
  • 为空 → 往下走优先级 2
→
优先级 2
utm_source
  • 命中 3 个 WhatsApp 类来源 → WHATSAPP-SUPERMOM
  • 命中 5 个邮件类来源 → EDM-SUPERMOM
  • 命中其余 28 个来源 → WEBSITE-SUPERMOM
  • 未匹配 → 往下走优先级 3
→
优先级 3
oldChannel
  • 仅当携带的 media 参数（sm_media 算出的结果）、utm_source、utm_medium 这三者全部为空 才生效
  • 注意：这里的"media"指的是请求里携带/已算出的 media 参数本身，不是 utm_medium —— utm_medium 是与它并列检查的第三个独立字段
  • #sleekflow → WHATSAPP-SUPERMOM
  • #EDM → EDM-SUPERMOM
  • #social* / #blog / #community / #CDPBanner → WEBSITE-SUPERMOM
→
最终兜底
三级都没命中
  • 统一兜底为 WEBSITE-SUPERMOM

5.逐个 API 详细逻辑

每个 API 统一用同一个结构看：没传任何参数时取什么 → 传了参数时怎么算 → 有没有特殊例外。

DORRA_MY

DorraMyApi.java 独立逻辑（仅 sm_media）
没有传 sm_media 时
直接取配置默认值（DORRA_MY.Media，通常为 SUPERMOM）
传了 sm_media 时，怎么算
  1. 小写后等于 supermom → WHATSAPP-SUPERMOM
  2. 其他任何非空值 → 原值直接透传，不转换
不依赖
不看 utm_source，不看 oldChannel
⚠ 特殊例外： 不管走哪条路，只要最终算出来的结果正好是 WEBSITE-SUPERMOM，系统会再把它强制改写成 SUPERMOM。这个 API 永远不会真正输出 WEBSITE-SUPERMOM。

DORRA_SG

DorraSgApi.java 标准三级逻辑
完全复用第 4 节「标准三级优先级逻辑」，没有任何额外例外或后置转换。三级都未命中时，兜底为 WEBSITE-SUPERMOM。

JONSSON_MY

JonssonMyApi.java 无条件覆盖为配置值
没有传任何参数时
取配置默认值（通常为 SUPERMOM）
传了 sm_media / utm_source 时，怎么算
不影响结果——这个 API 不读取 sm_media / utm_source / oldChannel，请求构造阶段会直接用配置值无条件覆盖掉之前的任何值
⚠ 业务提示： 排查这个 API 的 media 问题时，不要往 sm_media / utm_source 参数上找原因，只需要查配置项。

LondonWeight

LondonWeightApi.java 标准三级逻辑
完全复用第 4 节「标准三级优先级逻辑」，与 DORRA_SG 逻辑完全一致，没有任何额外例外。三级都未命中时，兜底为 WEBSITE-SUPERMOM。

NYSS_MY

NyssMyApi.java 无条件覆盖为配置值
没有传任何参数时
取配置默认值（通常为 SUPERMOM）
传了 sm_media / utm_source 时，怎么算
不影响结果——与 JONSSON_MY 逻辑完全一致，请求构造阶段直接用配置值无条件覆盖
⚠ 业务提示： 排查问题时不要往参数上找原因，只需要查配置项。

NYSS_SG

NyssSgApi.java 标准三级逻辑 + 后置转换
没有传任何参数时
先兜底为 WEBSITE-SUPERMOM；若流程结束后仍为空，再取配置默认值（NYSS_SG.Media）
传了参数时，怎么算
判断顺序与第 4 节「标准三级逻辑」完全相同（sm_media → utm_source → oldChannel）
⚠ 特殊例外： 只要算出来是 EDM-SUPERMOM，系统会强制改写成 WEBSITE-SUPERMOM。结果就是：NYSS_SG 永远不会出现 EDM-SUPERMOM，即便上游传的是邮件类 utm_source 或 oldChannel=#EDM。

YunNam

YunNamApi.java 独立逻辑（与其他 API 完全不同）
表单数据（formData）— 没传 utm_medium 时
直接默认给 WHATSAPP-SUPERMOM
表单数据（formData）— 传了 utm_medium 时
仅当 utm_medium = website 时 → 改为 WEBSITE-SUPERMOM；其他值不影响，仍是 WHATSAPP
Excel 导入数据 — 另一套独立逻辑
  1. 没传 media → 取配置默认值（YUN_NAM.Media）
  2. 传了 media，小写为 supermom → WHATSAPP-SUPERMOM
  3. 传了 media，其他非空值 → 原值透传
⚠ 特殊例外： 这是唯一一个"默认值是 WHATSAPP"的 API，方向和其他六个（默认 WEBSITE 或配置值）相反，且完全不参考 sm_media / utm_source / oldChannel 的标准判断顺序。表单数据和 Excel 导入数据走的是两套不同逻辑，不要混用理解。
