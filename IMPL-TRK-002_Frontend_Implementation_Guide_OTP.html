§1

通用规则General implementation rules

1.1 两个字段必须由每个触发点显式传入1.1 Two fields must be passed explicitly by every trigger point

source_component、component_name 不允许在弹窗组件内部通过路由或全局状态动态推断，必须由每一个触发 OTP 弹窗的按钮/组件在调用时显式传参。component_type 固定为常量 "otp_popup"，写死在弹窗组件内部即可。 source_component and component_name must never be inferred inside the popup component from the route or global state. Every button/component that triggers the OTP popup must pass them explicitly as call parameters. component_type is a fixed constant "otp_popup" — hardcode it inside the popup component. 

// 弹窗组件内部 —— 只负责接收参数并 push，不做任何推断// Inside the popup component — only receives params and pushes, no inference
function openOtpPopup({ sourceComponent, sourcePage, componentName, contentType }) {
  pushEvent({
    event: "otp_popup_view",
    page_type: getCurrentPageType(),
    component_type: "otp_popup",
    source_component: sourceComponent,
    ...(sourcePage && { source_page: sourcePage }),  // 仅 #1 会传，其余 13 个入口不传// only #1 passes this, the other 13 entries omit it
    component_name: componentName,
    ...(contentType && { content_type: contentType })
  });
}

这段是组件内部的通用写法，sourceComponent/componentName 只是形参名，不是具体值——具体传什么取决于是哪个按钮调用它。比如导航栏注册按钮，调用方要这样写： The snippet above is the generic implementation. sourceComponent/componentName are just parameter names, not actual values — what gets passed depends on which button calls it. For the nav bar register button, the caller looks like this: 

// 调用方（例：#1 导航栏注册按钮，唯一还需要传 sourcePage 的入口）// Caller (example: #1 nav bar register button — the only entry that still passes sourcePage)
onClick={() => openOtpPopup({
  sourceComponent: "navigation_register",
  sourcePage: "any",
  componentName: "navigation_register_btn",
})}
// 调用方（例：#2 首页 Hero AIMA —— 其余 13 个入口都不传 sourcePage）// Caller (example: #2 homepage hero AIMA — the other 13 entries don't pass sourcePage)
onClick={() => openOtpPopup({
  sourceComponent: "aima_open",
  componentName: "homepage_hero_chat",
})}

每一个触发点具体该填什么值，不用自己猜或去问产品——§2 已按 14 个入口逐一给出对应的调用示例，直接照抄对应那一段即可。 You don't need to guess or ask product what value each trigger point should use — §2 already gives a matching call example for all 14 entry points. Just copy the relevant one.

1.2 source_page 已简化为 #1 专用字段1.2 source_page is now specific to #1 only

已确认（原 §1.4 分析）：除 #1 外，其余 13 个入口的 source_page 值与同一事件自带的 page_type 完全重复，因此不再要求前端传这个字段。source_page 现在只在 #1 导航栏注册 这一个入口保留，固定传字面量 "any"——原因是这个按钮故意把所有触发页面聚合成一类，方便分析时不用按十几个页面拆开看，这是 page_type 无法替代的聚合设计。 Confirmed (formerly the §1.4 analysis): apart from #1, the source_page value on the other 13 entries fully duplicates the page_type already carried on the same event, so the frontend no longer needs to pass it. source_page now only applies to #1 nav bar register, always passing the literal "any" — this button deliberately aggregates all trigger pages into one bucket for analysis, which page_type alone can't replicate.

用 URL 做页面来源分析在技术上可行，但不建议——URL 比 page_type 脏得多（带 /beta/ 环境前缀、query string、多语言路径），在 BigQuery 里再解析一遍容易出错，page_type 是已经清洗过的标准字段，应优先使用。 Using the URL for page-source analysis is technically possible but not recommended — URLs are much noisier (env prefixes like /beta/, query strings, locale paths) and re-parsing them in BigQuery is error-prone. page_type is the already-cleaned standard field and should be preferred.

1.3 content_type 在指定场景下为必填字段1.3 content_type is required in a specific scenario

规则：当 component_name = "detail_aima_widget" 时，otp_popup_view 必须同时携带 content_type 字段（取值 "flashcard" 或 "article"）。原因：闪卡详情页和文章详情页的 Aima 聊天入口使用相同的 component_name，仅靠基础字段无法区分触发页面类型。 Rule: when component_name = "detail_aima_widget", otp_popup_view must also carry content_type (value "flashcard" or "article"). Reason: the Aima chat entry on the flashcard detail page and on the article detail page share the same component_name — the base fields alone can't distinguish which page type triggered it.

§3

下游事件同步要求Downstream event sync requirements

OTP 流程完成后触发的 sign_up、login 事件，需要携带与本次流程起始的 otp_popup_view 相同的 source_component 值；若本次流程是 #1（唯一携带 source_page 的入口），source_page 也要一并同步。前端需要在弹窗打开时用 state 保存这些值，一直持有到验证完成、推送事件时复用同一份值，不要重新计算。 The sign_up/login events fired after the OTP flow completes must carry the same source_component as the otp_popup_view that started this flow. If this flow was #1 (the only entry that carries source_page), source_page must be synced too. The frontend must save these values in state when the popup opens, hold them until verification completes, and reuse the same values when pushing the event — never recompute. 

function openOtpPopup({ sourceComponent, sourcePage, componentName, contentType }) {
  otpContext = { sourceComponent, sourcePage, contentType };  // 存进 state，sourcePage/contentType 一并存（多数情况下为 undefined）// saved to state, sourcePage/contentType included too (usually undefined)
  pushEvent({
    event: "otp_popup_view",
    page_type: getCurrentPageType(),
    component_type: "otp_popup",
    source_component: sourceComponent,
    ...(sourcePage && { source_page: sourcePage }),
    component_name: componentName,
    ...(contentType && { content_type: contentType })
  });
}

// 验证完成后，sign_up / login 复用同一份 state，sourcePage/content_type 同样要带上（有值才带）// After verification, sign_up / login reuse the same state, sourcePage/content_type included too (only when present)
pushEvent({
  event: "sign_up", page_type: getCurrentPageType(),
  method: "otp", otp_channel: "sms",
  source_component: otpContext.sourceComponent,
  ...(otpContext.sourcePage && { source_page: otpContext.sourcePage }),
  ...(otpContext.contentType && { content_type: otpContext.contentType })
});
补充规则：若本次 OTP 流程由 #11/#12（detail_aima_widget）触发，content_type 要跟着 source_component 一起存进 state，并同步出现在 sign_up/login 事件里，不能只在 otp_popup_view 那一步携带。 Additional rule: if this OTP flow was triggered by #11/#12 (detail_aima_widget), content_type must be saved to state alongside source_component, and must appear in the sign_up/login event too — not just at the otp_popup_view step.

对照组：若用户是从 #1（导航栏注册按钮，唯一携带 sourcePage 的入口）触发的，otpContext.sourcePage 有值（"any"），...(otpContext.sourcePage && {...}) 这行展开式就会生效，sign_up 里会出现 source_page: "any"；其余 13 个入口该字段始终为 undefined，自动跳过，不需要为每个入口单独写判断逻辑。 Control case: if the user was triggered from #1 (nav bar register, the only entry with sourcePage), otpContext.sourcePage holds a value ("any"), so the spread ...(otpContext.sourcePage && {...}) kicks in and sign_up will include source_page: "any". 同一份 source_component 值，前端还需要在调用验证 OTP 接口（/api/otp/verify）时作为请求参数一并传给后端，用于新用户注册时写入 t_account.signup_entry_point。这是接口契约变更，需要后端单独排期实现。 The same source_component value also needs to be passed by the frontend as a request parameter when calling the OTP verification endpoint (/api/otp/verify), so the backend can write it to t_account.signup_entry_point on new user creation. This is an API contract change and needs to be scheduled separately on the backend.

分给三方看的话：前端只关心青色部分（触发时机、state 保存、事件推送）；后端只关心紫色部分（验证接口逻辑、新老用户分支、写库时机）；测试只关心琥珀色的两个验证点，两个都要过，缺一不可——只查 dataLayer 不代表数据库真的写进去了。 Split by audience: frontend only needs the teal part (trigger timing, state storage, event push); backend only needs the purple part (verify endpoint logic, new/existing user branch, write timing); QA only needs the two amber checkpoints — both must pass, neither is optional. Checking the dataLayer alone doesn't prove the database was actually written.

  2. 仅 #1 额外携带 source_page: "any"；其余 13 个入口的 otp_popup_view 中不应出现 source_page 字段Only #1 additionally carries source_page: "any"; the other 13 entries' otp_popup_view should not include a source_page field at all
  3. 第 11、12 行额外携带 content_type 字段，值分别为 "flashcard"/"article"Rows 11 and 12 additionally carry content_type, with values "flashcard"/"article" respectively
  4. 完成 OTP 流程后触发的 sign_up/login 事件，携带的 source_component 与本次流程起始的 otp_popup_view 一致；若触发来源是 #1，source_page 也要同步出现sign_up/login events fired after the OTP flow completes carry source_component matching the otp_popup_view that started the flow; if the trigger was #1, source_page must be synced too
  5. 若触发来源是 #11/#12（detail_aima_widget），sign_up/login 事件也要携带对应的 content_type（"flashcard"/"article"），不能只在 otp_popup_view 里出现If the trigger source is #11/#12 (detail_aima_widget), sign_up/login events must also carry the matching content_type ("flashcard"/"article") — not only in otp_popup_view
