Re-entry — What It Is & Why It Matters Re-entry（重入）— 这个功能是什么，为什么要做
For business stakeholders · Read this page only if you're short on time 写给业务方 · 时间紧张只看这一页就够了
Currently, once a user enters a Marketing Automation flow, she can never enter it again — even if her situation changes. For a pregnancy app, this means a user who received "third trimester" messages at 100 days before her due date will never automatically receive "final countdown" messages at 80 days — the system has already marked her as "done".

This feature introduces Re-entry: the ability for the same user to re-enter a flow when her EDD (Estimated Due Date) moves into a new configured range. The system evaluates every user's EDD every day and automatically triggers the right messages at the right time — with no manual intervention required. 目前，用户一旦进入 Marketing Automation Flow，就再也无法进入同一个 Flow——即使她的情况发生了变化。对于母婴 App 来说，这意味着一个在预产期前 100 天收到"孕晚期"内容的用户，永远不会自动收到预产期前 80 天的"最后冲刺"内容——系统已经认为她"走完了"。

这个功能引入了 Re-entry（重入）：当用户的 EDD（预产期）进入新的配置区间时，系统允许她再次进入 Flow。系统每天评估所有用户的 EDD，在正确的时间自动触发正确的消息——无需运营手动干预。
😓
Before Re-entry 没有 Re-entry 之前
User enters once, receives one batch of messages. Miss every milestone after that. Operator must manually re-enroll her. 用户只进入一次，只收到一批消息。之后所有里程碑全部错过，运营需要手动重新加入。
🎯
With Re-entry 有了 Re-entry 之后
User automatically re-enters when EDD hits a new range. Right message, right time, zero manual work. 用户 EDD 进入新区间时自动重入，在正确的时间收到正确的消息，运营零干预。
🛡️
Safe by Design 内置防护机制
Users won't receive duplicate messages. The system blocks re-entry until the previous journey completes. 用户不会收到重复消息。前一次旅程完成前，系统自动阻断新的进入。

Background 背景 背景

Marketing Automation flows currently support single-entry only. Once a user completes, exits, or fails a flow, they cannot re-enter — even if they later meet the trigger condition again. This limits the ability to deliver timely, condition-driven communications to users at different lifecycle stages.
Marketing Automation Flow 目前仅支持单次进入。用户完成、退出或失败后，即使再次满足触发条件，也无法重新进入 Flow，导致无法在用户不同生命周期阶段持续进行精准触达。
Problem Statement / 问题描述
Users who meet a condition again (e.g. EDD range re-entry) cannot be automatically re-enrolled. Operators must manually intervene. Single-entry flows cannot support multi-stage pregnancy journey communications or recurring lifecycle triggers.
用户再次满足条件（如 EDD 区间重入）时无法被自动重新加入 Flow，运营人员需手动干预。单次进入无法支持多阶段妊娠旅程通讯或周期性生命周期触发需求。
核心目标 · Objective Introduce a Re-entry mechanism driven by Time-based Condition evaluation, allowing users to re-enter a flow when they newly meet a time-based condition (e.g. EDD falls into a configured day range), with full concurrency control to prevent over-messaging. 引入基于 Time-based Condition 评估的 Re-entry 机制，当用户新满足时间条件（如 EDD 进入配置的天数区间）时自动重新进入 Flow，并通过并发控制防止过度触达。

User Story & Worked Examples 用户故事与场景举例

This section walks through real business scenarios to help non-technical readers understand exactly when Re-entry fires, when it is blocked, and why.
本节通过真实业务场景，帮助非技术读者直观理解 Re-entry 在什么情况下触发、什么情况下被阻断，以及背后的原因。
2.1 User Story 2.1 用户故事
🤰 As a Marketing Operator, I want to automatically send different messages to a pregnant user as her EDD approaches different milestone ranges — without having to manually re-enroll her each time. 作为运营人员，我希望随着孕妈 EDD 不断临近不同里程碑区间，系统能自动发送对应阶段的消息——无需每次手动重新加入。
Background: A pregnancy app has a Flow called "Prenatal Journey". It has three EDD-based branches:
  • Branch 1: EDD 86–120 days from now → send "Prepare for your third trimester" content
  • Branch 2: EDD 75–85 days from now → send "Your baby is almost here" content
  • Else: No content sent (user not yet in any range)

Without Re-entry: A user who enters Branch 1 at 90 days out can never enter Branch 2 at 80 days out — she only ever receives the first batch of messages, missing the second milestone entirely.

With Re-entry (Time-based Condition): When the user's EDD naturally falls into a new range she hasn't been enrolled in before, the system automatically creates a new entry for her — she receives the right message at the right time, automatically. 背景：某母婴 App 有一个名为"产前旅程"的 Flow，包含三个 EDD 分支：
  • Branch 1：EDD 距今 86–120 天 → 发送"备战孕晚期"内容
  • Branch 2：EDD 距今 75–85 天 → 发送"宝宝快来了"内容
  • Else：不在任何区间，不发送内容

无 Re-entry 时：用户在 EDD 还有 90 天时进入 Branch 1，之后即便 EDD 缩短到 80 天进入 Branch 2 的范围，系统也不会再次触达——她永远只收到第一批消息，错过第二个里程碑。

启用 Re-entry（Time-based Condition）后：当用户的 EDD 自然落入她尚未进入过的新区间时，系统自动为她创建新的进入记录——在正确的时间，自动发送正确的消息。

2.4 What Will NOT Trigger Re-entry 2.4 什么情况下不会触发 Re-entry
❌ These scenarios will NOT create a new enrollment ❌ 以下场景不会创建新的进入记录
  • Same branch condition within this flow, regardless of run state — If a user already entered via "EDD 86–120 days" in this flow, she won't re-enter that same branch even after Entry #1 Completes. Only entering a new branch range (e.g. "EDD 75–85 days") triggers re-entry. Note: entering the same flow via the same condition in a different flow is allowed. 此 Flow 内相同分支条件，无论运行状态 — 用户已通过此 Flow 中的"EDD 86–120 天"分支进入过，即使进入 #1 已完成，该分支也不会再次触发。只有进入新的分支区间（如"EDD 75–85 天"）才触发重入。注意：在不同 Flow 中通过相同条件进入不受此限制。
  • EDD outside all branch ranges — If the user's EDD falls into the Else range (e.g. 200 days away), no enrollment is created. Else catches the user but does not trigger re-entry. EDD 不在任何分支区间内 — 用户 EDD 落入 Else 区间（如距今 200 天），不创建进入记录。Else 捕获用户但不触发重入。
  • Previous run is still Running — No new enrollment until the current run reaches Completed / Exited / Failed. 前次运行仍在 Running — 在当前运行达到 Completed / Exited / Failed 之前，不创建新进入。
  • Allow Re-entry is OFF — The flow behaves as single-entry. No re-entry logic is evaluated. Allow Re-entry 未开启 — Flow 保持单次进入行为，不执行任何重入评估逻辑。

3.2 Re-entry Trigger Basis 3.2 Re-entry 触发方式
Business Rule: A new entry is created only when the user newly meets the time-based condition — i.e. transitions from "not meeting the condition" → "newly meeting the condition". Repeated matches of the same condition do not trigger re-entry. 业务规则： 只有当用户从"不满足条件" → "新满足条件"时，才触发新的进入。重复满足同一条件不触发 Re-entry。
Option / 选项 说明 Description / 描述 Phase / 阶段
Time-based Condition 基于时间条件 A new entry is created only when the user newly meets the condition based on time evaluation (recommended). Evaluated continuously — does not rely on list updates. 仅当用户新满足基于时间评估的条件时创建新进入（推荐）。持续评估，不依赖列表更新。 Phase 1

3.4 Concurrency Control 3.4 并发控制
Three immutable concurrency rules govern how re-entry interacts with existing active runs. These rules cannot be configured by the operator.
三条固定并发控制规则，定义 Re-entry 与现有运行中记录的交互方式。运营人员无法修改这些规则。
# Rule / 规则 说明 Behavior / 行为 Example / 举例
R1 Do not re-enter while previous run is still Running 上一次运行中时不重入 前次 Running 时禁止重入 If a user has an active Running enrollment, any new trigger is blocked until the run completes. 用户有 Running 状态的进入记录时，新触发被阻断，直至该次运行结束。 4/1 → Entry #1 (Running) · 4/5 → trigger fires → ❌ blocked 4/1 → 进入 #1（Running）· 4/5 → 触发条件 → ❌ 不进入
R2 Do not re-enter for the same condition (Flow-level) 相同条件不重入（Flow 级别） 同一 Flow 内同一 Branch 只进入一次 Within the same flow, if a user has already entered via a specific branch condition (e.g. "EDD 86–120 days"), she will not re-enter that same branch again — regardless of run state. Only entering a different branch condition triggers re-entry. Scope: Flow-level only. Cross-flow re-entry is not restricted. 在同一 Flow 内，用户已通过某个分支条件进入过（如"EDD 86–120 天"），则不再重入该分支——无论前次运行状态如何。只有进入不同分支条件才触发重入。范围：仅限 Flow 级别。跨 Flow 不受限制。 Entry for "EDD 86–120 days" already exists in this flow → same branch → ❌ blocked · Entry for "EDD 75–85 days" (different branch) → ✅ allowed 此 Flow 内已有"EDD 86–120 天"的进入记录 → 同一分支 → ❌ 不进入 · "EDD 75–85 天"（不同分支）→ ✅ 允许
R3 Allow re-entry after Completed / Exited / Failed Completed / Exited / Failed 后允许重入 终态后新条件可重入 Once a previous run reaches a terminal state (Completed, Exited, or Failed), and the user newly meets a condition, re-entry is permitted. 当前次运行达到终态（Completed / Exited / Failed），且用户新满足条件时，允许重入。 Entry #1 Completed · user enters "EDD 75–85 days" range → ✅ new entry created 进入 #1 已完成 · 用户进入"EDD 75–85 天"区间 → ✅ 创建新进入
No parallel runs: A user can only have one Running enrollment at a time in any given flow. Concurrent active entries are not permitted. 无并行运行： 同一用户在同一 Flow 中，同一时间只能有一条 Running 状态的进入记录，不允许并发活跃进入。
✅ Phase 1 Confirmed Decisions · 已确认决策
  • R2 scope — Flow-level: Same user, same flow, same branch condition = blocked. Cross-flow entries are always independent and unrestricted. R2 范围 — Flow 级别： 同一用户在同一 Flow 内，同一分支条件只进入一次。跨 Flow 的进入完全独立，不受限制。

A.2 Daily Evaluation — Suggested Logic A.2 每日评估 — 建议逻辑
Runs once per day as a batch job. The following pseudocode illustrates the evaluation sequence — the actual implementation may differ.
每日作为批量任务运行一次。以下伪代码展示评估顺序，实际实现方式可能不同。
Pseudocode — Daily Re-entry Evaluation / 每日 Re-entry 评估伪代码
-- Runs daily, e.g. UTC+8 00:00–02:00
-- 每日运行，如 UTC+8 00:00–02:00

FOR EACH flow WHERE allow_reentry = true AND status = 'active':

  FOR EACH user IN flow.eligible_users:

    today_edd_days = DATEDIFF(user.edd, TODAY)  -- days until EDD

    -- Step 1: Find the first matching branch (sort_order ASC)
    -- 步骤 1：找到第一个匹配的分支（按 sort_order 升序）
    matched_branch = NULL
    FOR EACH branch IN flow.branches WHERE branch_type = 'condition'
                                    ORDER BY sort_order ASC:
      IF today_edd_days >= branch.edd_min_days
         AND today_edd_days <= branch.edd_max_days:
        matched_branch = branch
        BREAK

    -- Step 2: If no branch matched, user is in Else → skip, no enrollment
    -- 步骤 2：无匹配分支 → 用户在 Else 状态，跳过，不创建 enrollment
    IF matched_branch IS NULL: CONTINUE

    -- Step 3: R1 — Block if user has a Running enrollment in this flow
    -- 步骤 3：R1 — 用户在此 Flow 有 Running 记录则阻断
    IF EXISTS enrollment WHERE flow_id = flow.id
                          AND user_id = user.id
                          AND status = 'running':
      CONTINUE  -- blocked by R1

    -- Step 4: R2 — Block if user already entered this flow via this branch
    -- 步骤 4：R2 — 用户在此 Flow 内已通过该分支进入过则阻断
    IF EXISTS enrollment WHERE flow_id = flow.id
                          AND user_id = user.id
                          AND branch_id = matched_branch.id:
      CONTINUE  -- blocked by R2 (flow-level, same branch)

    -- Step 5: R3 — Previous run must be in terminal state (or no prior run)
    -- 步骤 5：R3 — 前次运行需为终态（或无历史记录）
    last_enrollment = SELECT * FROM enrollment
                      WHERE flow_id = flow.id AND user_id = user.id
                      ORDER BY enrolled_at DESC LIMIT 1

    IF last_enrollment IS NOT NULL
       AND last_enrollment.status = 'running':
      CONTINUE  -- already caught by R1, defensive check

    -- Step 6: All checks passed → create new enrollment
    -- 步骤 6：所有检查通过 → 创建新 enrollment
    CREATE enrollment:
      flow_id      = flow.id
      user_id      = user.id
      branch_id    = matched_branch.id
      entry_number = COUNT(existing enrollments for this user/flow) + 1
      status       = 'running'
      enrolled_at  = NOW()
      edd_snapshot = user.edd
EDD data source: The evaluation uses the user's current EDD value at the time of the daily job — not a snapshot from a previous date. If a user updates her EDD, the new value takes effect in the next daily evaluation cycle. EDD 数据来源： 评估使用每日任务执行时用户的当前 EDD 值，而非历史快照。如果用户更新了 EDD，新值在下一个每日评估周期生效。
A.3 R2 Judgment — How "Same Branch" Is Determined A.3 R2 判断 — "相同分支"如何认定
R2 blocks re-entry when a user has already been enrolled via the same branch within the same flow. The judgment is based on branch_id — not on day range string matching.
R2 在用户已通过同一 Flow 内同一分支进入过时阻断重入。判断依据是 branch_id，而非天数区间字符串匹配。
Scenario / 场景 说明 R2 Result / R2 判断 Reason / 原因
User previously enrolled via Branch 1 (86–120 days). EDD still in 86–120 range. 用户已通过 Branch 1（86–120天）进入过，EDD 仍在 86–120 天区间。 已通过 Branch 1 进入，EDD 未变 ❌ Blocked Same branch_id already exists in enrollment table for this user + flow enrollment 表中已存在该用户 + 该 Flow + 相同 branch_id 的记录
User previously enrolled via Branch 1. EDD has now moved into Branch 2 range (75–85 days). 用户已通过 Branch 1 进入，EDD 已进入 Branch 2 区间（75–85天）。 Branch 1 已进入，EDD 进入 Branch 2 ✅ Allowed Different branch_id — Branch 2 has never been enrolled in this flow 不同 branch_id，Branch 2 在此 Flow 内从未进入过
Operator edits Branch 1 day range from 86–120 to 80–120. User had already entered the old Branch 1. 运营将 Branch 1 天数从 86–120 改为 80–120，用户已进入过旧的 Branch 1。 分支配置修改后，用户已进入过该分支 ❌ Blocked branch_id is unchanged even if the range is edited — same branch ID = still blocked branch_id 不因区间修改而变化，同一 branch_id = 仍然阻断
User enrolled via Branch 1 in Flow A. Same user, same branch range configured in Flow B. 用户在 Flow A 通过 Branch 1 进入，Flow B 中配置了相同天数区间的分支。 跨 Flow 相同区间 ✅ Allowed R2 is scoped to one flow. Cross-flow entries are always independent. R2 仅限 Flow 内，跨 Flow 进入完全独立。
A.4 Branch Range Overlap Validation A.4 分支区间重叠校验
Triggered on flow save. Can be implemented on the frontend, backend, or both. Suggested logic:
在 Flow 保存时触发，可在前端、后端或两者同时实现。建议逻辑如下：
Pseudocode — Overlap Detection / 重叠检测伪代码
-- Check all condition branches (exclude Else) for overlapping ranges
-- 检查所有 condition 分支（排除 Else）是否有区间重叠

branches = GET all branches WHERE branch_type = 'condition'
           ORDER BY edd_min_days ASC

overlaps = []

FOR i IN 0..len(branches)-2:
  a = branches[i]
  b = branches[i+1]

  -- Two ranges overlap if one starts before the other ends
  -- 若一个区间在另一个结束前开始，则重叠
  IF a.edd_max_days >= b.edd_min_days:
    overlaps.append({
      branch_a: a.id,
      branch_b: b.id,
      overlap_range: [b.edd_min_days, a.edd_max_days]
    })

IF len(overlaps) > 0:
  -- Return warning — do not block save, but surface to operator
  -- 返回警告——不阻断保存，但向运营人员展示警告弹窗
  RETURN { warning: true, overlaps: overlaps }
⚠ Warning vs Hard Block: Overlap detection shows a warning dialog — it does not hard-block the save. Operators can acknowledge and save anyway (at their own risk). Publishing a flow with overlapping ranges is allowed, with first-match-wins applied at evaluation time. Consider adding a stronger warning or block at publish time. ⚠ 警告 vs 强制阻断： 重叠检测展示警告弹窗，不强制阻断保存。运营人员可确认后继续保存（风险自担）。存在重叠区间的 Flow 允许发布，评估时采用第一匹配优先原则。可考虑在发布时加强警告或设为强制阻断。
A.5 Else Branch — Implementation Note A.5 Else 分支 — 实现说明
Behavior / 行为 说明 Implementation Note / 实现说明
Else does NOT create an enrollment record Else 不创建 enrollment 记录 不写入 enrollment 表 When the daily evaluation finds no matching condition branch, the user is skipped entirely. No row is written to the enrollment table. The user remains in an implicit "waiting" state. 每日评估未找到匹配的 condition 分支时，直接跳过该用户，不向 enrollment 表写入任何记录。用户处于隐式"等待"状态。
Else → Branch transition triggers re-entry Else → Branch 转变触发重入 视为新满足条件 Because no enrollment record exists for Else, the R2 check finds no prior entry for the matched branch — re-entry is allowed. No special "Else state" tracking is required. 由于 Else 未创建 enrollment 记录，R2 检查找不到该分支的历史进入记录，重入被允许。无需额外追踪"Else 状态"。
Else branch cannot be deleted Else 分支不可删除 前端禁用删除操作 Enforced at the UI level — delete action is disabled for branch_type = 'else'. Can also add a backend guard to reject DELETE requests for Else branches. 在 UI 层强制执行，branch_type = 'else' 的分支删除操作置灰。也可在后端添加防护，拒绝 Else 分支的 DELETE 请求。
A.6 Key Query References A.6 关键查询参考
SQL — Entries (per user, max)
-- Workflow List: Entries (per user, max) per flow
SELECT MAX(entry_count) AS entries_per_user_max
FROM (
  SELECT user_id, COUNT(*) AS entry_count
  FROM enrollment
  WHERE flow_id = :flow_id
  GROUP BY user_id
) sub
SQL — Metrics Summary (Enrolled Total / Unique Users / Avg)
SELECT
  COUNT(*)                          AS enrolled_total,
  COUNT(DISTINCT user_id)           AS unique_users,
  ROUND(COUNT(*) * 1.0
        / NULLIF(COUNT(DISTINCT user_id), 0), 1)
                                    AS avg_entries_per_user,
  MAX(user_entry_counts.cnt)        AS entries_per_user_max
FROM enrollment
LEFT JOIN (
  SELECT user_id, COUNT(*) AS cnt
  FROM enrollment WHERE flow_id = :flow_id GROUP BY user_id
) user_entry_counts USING (user_id)
WHERE flow_id = :flow_id
SQL — R1 Check (is user currently Running?)
-- Returns true if user has a Running enrollment → block re-entry
SELECT EXISTS (
  SELECT 1 FROM enrollment
  WHERE flow_id = :flow_id
    AND user_id  = :user_id
    AND status   = 'running'
) AS is_running
SQL — R2 Check (has user entered this branch before?)
-- Returns true if user already entered this branch → block re-entry
SELECT EXISTS (
  SELECT 1 FROM enrollment
  WHERE flow_id   = :flow_id
    AND user_id   = :user_id
    AND branch_id = :matched_branch_id
) AS already_entered_branch

Glossary 术语表

Term / 术语 Definition (EN) 定义（中文）
Re-entry The ability for a user to enter a flow more than once, triggered by meeting a new condition. 用户在满足新条件时，多次进入同一 Flow 的能力。
Time-based Condition A trigger type evaluated continuously based on time-sensitive attributes (e.g. EDD day range). Fires when a user newly meets the condition. 基于时间敏感属性（如 EDD 天数区间）持续评估的触发类型，用户新满足条件时触发。
EDD Estimated Due Date — the user's expected pregnancy delivery date, used as the primary time-based attribute. 预产期（Estimated Due Date）——用户预计分娩日期，用作主要的时间属性。
Enrollment A single entry event of a user into a flow. Multiple enrollments can exist per user if Re-entry is enabled. 用户进入 Flow 的单次事件。启用 Re-entry 后，同一用户可有多条进入记录。
Concurrency Control Rules that govern whether a new enrollment is allowed when a user already has an active run in the same flow. 控制同一用户在同一 Flow 已有活跃运行时，是否允许新进入的规则集。
Branch A conditional path in the flow, defined by an EDD day range. Users are routed to the first matching branch. Flow 中由 EDD 天数区间定义的条件路径，用户被路由至第一个匹配的分支。
Else Branch The permanent fallback branch that catches users who do not match any configured EDD range. Cannot be deleted. 永久兜底分支，捕获不匹配任何已配置 EDD 区间的用户，不可删除。
Running The active state of an enrollment — the user is currently progressing through the flow. 进入记录的活跃状态，用户正在 Flow 中运行。
Enrolled Total Total count of all enrollment events for a flow, including re-entries. Not deduplicated. Flow 的所有进入事件总数，含重入，非去重。
Unique Users Count of distinct users who have entered a flow at least once. 至少进入过一次 Flow 的去重用户数。
User Journey A chronological view of all enrollment records for a specific user in a specific flow. 特定用户在特定 Flow 中所有进入记录的时间顺序视图。
