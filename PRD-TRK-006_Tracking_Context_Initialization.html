01

Background

The system currently lacks a unified Identity Tracking Flow, resulting in fragmented user identity across platforms and preventing reliable behavioral attribution.
Problem Statement
Anonymous users cannot be stably identified across sessions. Pre-login and post-login behaviors cannot be linked. GA4 identity and internal system identity are misaligned. Audience Gallery cannot accumulate a complete user behavioral chain. Multi-platform tracking standardization is blocked.
核心问题 · Key Problem 当前系统缺少统一的 Identity Tracking Flow：匿名用户无法稳定识别，登录前后行为无法关联，GA4 与内部系统 identity 无法统一，导致 Audience Gallery 与多平台 tracking 无法落地。

Industry Standard Reference: This design is based on established CDP / analytics standards — Google Analytics client_id model, Segment anonymousId + userId stitching, Mixpanel distinct_id merge, Amplitude anonymous → identified merge, and Meta / TikTok Pixel identity matching best practices.

Core Identity Design

The system operates with two distinct identity types that must never be conflated.
Identity TypePurpose用途说明Source来源Lifecycle生命周期
anonymous_idAnonymous user identity, pre-login behavior tracking匿名用户身份标识，用于登录前行为追踪GA4 client_id复用 GA4 client_idStable across login — never regenerated登录后保持不变，绝不重新生成
hashed_uidLogged-in user identity, cross-platform consistency登录用户身份标识，用于跨平台 identity 一致性Backend — login API response后端登录接口返回Present only when user is authenticated仅在用户已登录时存在
Core Rule: Anonymous Identity and Logged-in Identity must be maintained separately. anonymous_id must remain stable. After login, anonymous_id must NOT change. Identity stitching is exclusively a Backend responsibility.
2.1 anonymous_id
Used for anonymous user behavior tracking, pre-login signal accumulation, and anonymous → uid stitching.
RuleDetail说明

2.2 hashed_uid
Used for logged-in identity, internal identity mapping, and cross-platform identity consistency.
RuleDetail说明
Raw UID ExposureOriginal v2 uid must NEVER be uploaded to any third-party tracking platform原始 v2 uid 严禁上传至任何第三方 tracking 平台
ConsistencySame uid must always produce the same hashed_uid同一个 uid 必须始终生成相同的 hashed_uid

为什么必须用 Hashed UID 真实 uid 是内部主键，不能暴露给 GA4、GTM、TikTok、Meta 等第三方平台。使用 SHA-256 对 uid 直接哈希生成 hashed_uid，既能防止 identity leakage，又符合行业最佳实践（hashed email / hashed internal id），同时支持稳定的跨平台 identity matching。

2.4 Session Restore Specification — hashed_uid on Page Refresh
页面刷新后 sessionStorage 被清空，hashed_uid 不能从客户端恢复。前端必须在初始化阶段通过 session 恢复接口重新获取。
RuleDetail规范说明

JavaScriptPage refresh — hashed_uid restore before initTracking()
async function restoreSession() {
  try {
    const res = await fetchWithTimeout('/api/auth/session', { timeout: 3000 });
    if (res?.user?.hashed_uid) {
      sessionStorage.setItem('hashed_uid', res.user.hashed_uid); // restore to sessionStorage
      return res.user.hashed_uid;
    }
  } catch (e) {
    console.warn('[Tracking] session restore failed', e); // silent fail — proceed as anonymous
  }
  return null;
}

// Page load entry point — restore BEFORE initTracking
const hashedUid = await restoreSession();
await initTracking(hashedUid); // hashed_uid passed in, not re-fetched inside
Session restore API response — Backend must return hashed_uid in the same format as the login API response. If the existing session endpoint does not currently include this field, Backend must add it before frontend implementation begins.

04

Tracking Flows

Three distinct flows cover all user entry states. The state machine below shows the complete decision logic — followed by per-flow detail.
三种 Flow 核心要点 无论哪种 Flow，anonymous_id 和 session_id 在整个 session 内必须保持不变。登录后只是新增 hashed_uid，绝不能重建 anonymous_id，否则行为链路断裂，stitching 失败。
Flow State Machine
Three Flow State Machine — User Entry × Login State
4.1 Flow 1 — Anonymous User Visit
User arrives at the page without an active session. Tracking context is initialized with anonymous identity only.
JavaScriptdataLayer push — tracking_initialized (anonymous)
dataLayer.push({
  event: "tracking_initialized",
  anonymous_id: "<GA4 client_id>",   // from gtag('get', ..., 'client_id')
  session_id: "<GA4 ga_session_id>", // from gtag('get', ..., 'session_id')
  login_status: "anonymous"
  // hashed_uid is omitted — user not logged in
});
System records anonymous_id, session_id, and all anonymous behavior events. No UID stitching is triggered at this stage.
4.2 Flow 2 — User Already Logged In on Arrival
User enters the page with an active session. Both anonymous identity and hashed_uid are included in the initialization event.
JavaScriptdataLayer push — tracking_initialized (logged_in)
dataLayer.push({
  event: "tracking_initialized",
  anonymous_id: "<GA4 client_id>",
  session_id: "<GA4 ga_session_id>",
  hashed_uid: "<hashed_uid from login API>",
  login_status: "logged_in"
});
Backend can immediately establish the anonymous_id → hashed_uid identity relationship on receiving this event.
4.3 Flow 3 — Anonymous User Logs In During Session
User was anonymous on arrival but completes login during the session. A login event is pushed — using the exact same IDs from initialization.
JavaScriptdataLayer push — login event
dataLayer.push({
  event: "login",
  anonymous_id: "<SAME GA4 client_id as tracking_initialized>", // ← must be identical
  session_id: "<SAME GA4 ga_session_id>",                       // ← must be identical
  hashed_uid: "<hashed_uid from login API response>",
  login_status: "logged_in"
});
Critical — never regenerate IDs after login: Do NOT re-fetch anonymous_id or session_id after login. Regenerating either ID will break the anonymous behavior chain, cause identity stitching to fail, corrupt attribution, and rupture Audience Gallery behavioral history.
⚠ 登录后绝不能重新生成 anonymous_id / session_id，否则匿名行为链路断裂，stitching 失败，attribution 错误。

GA4 Client ID — Retrieval Specification

GA4 client_id is retrieved asynchronously. The following spec defines timeout handling, fallback strategy, and timing requirements.
Retrieval Timing & Timeout Flow
GA4 Client ID Async Retrieval — Timeout & Fallback Decision
JavaScriptGA4 Client ID — Timeout-safe retrieval
const getGA4ClientId = () => new Promise((resolve) => {
  const timer = setTimeout(() => resolve(null), 3000); // 3s timeout
  gtag('get', 'G-XXXXXXX', 'client_id', (clientId) => {
    clearTimeout(timer);
    resolve(clientId);
  });
});

const getGA4SessionId = () => new Promise((resolve) => {
  const timer = setTimeout(() => resolve(null), 3000);
  gtag('get', 'G-XXXXXXX', 'session_id', (sessionId) => {
    clearTimeout(timer);
    resolve(sessionId);
  });
});

async function initTrackingContext(hashedUid) {
  try {
    const [clientId, sessionId] = await Promise.all([
      getGA4ClientId(), getGA4SessionId()
    ]);
    dataLayer.push({
      event: "tracking_initialized",
      anonymous_id: clientId ?? undefined,   // null → undefined, not UUID fallback
      session_id: sessionId ?? undefined,
      ...(hashedUid && { hashed_uid: hashedUid }),
      login_status: hashedUid ? "logged_in" : "anonymous"
    });
  } catch (e) {
    console.warn('[Tracking] init failed', e); // silent fail — never block
  }
}
Fallback rule: When GA4 is unavailable, anonymous_id is omitted (undefined). Frontend must NOT substitute a self-generated UUID — this would pollute the identity graph with phantom anonymous IDs that can never be stitched.

GA4 Session ID — Lifecycle Specification

GA4 session_id is session-scoped and expires after 30 minutes of inactivity. The following rules govern its use across navigation patterns.

Error Handling & Fallback Strategy

Tracking failures must never affect the primary business flow. All tracking logic is wrapped in error isolation.
降级原则 Tracking 是观测层，不是业务层。任何 tracking 异常都应静默失败（silent fail），不能阻塞页面渲染、登录流程、或其他核心功能。try/catch 是强制要求，不是可选项。

7.1 Supplemental Login Event Specification
当登录接口在推送 login event 时尚未返回 hashed_uid（超时或延迟），前端先推送不含 hashed_uid 的事件，待接口返回后补发完整 login event。
StepActionOwner说明
1 — 立即推送Push login event with login_status: logged_in but without hashed_uid — do NOT wait for APIFrontend登录成功后立即推送，不等待 hashed_uid 接口返回，不阻塞登录流程
2 — 等待接口Continue waiting for hashed_uid API response in background (max 10s timeout)Frontend后台等待接口返回，最长等待 10 秒，超时后放弃补发
3 — 补发事件When API resolves: push supplemental login event with complete payload including hashed_uidFrontend接口返回后补发完整 login event，包含 hashed_uid
4 — 后端处理Backend receives supplemental event — uses anonymous_id + session_id to match with the earlier incomplete event and complete stitchingBackend后端收到补发事件后，通过 anonymous_id + session_id 与之前的不完整事件匹配，完成 stitching
5 — 超时放弃If API does not resolve within 10s — silent abandon. Backend identity stitching will complete on next page load when session restore returns hashed_uid.Frontend10 秒超时后静默放弃，下次页面加载时 session restore 会带回 hashed_uid 完成 stitching
JavaScriptSupplemental login event — push immediately then supplement on resolve
async function onLoginSuccess(cachedClientId, cachedSessionId, hashedUidPromise) {

  // Step 1: push immediately without hashed_uid — do NOT block
  dataLayer.push({
    event:        "login",
    anonymous_id: cachedClientId  ?? undefined,
    session_id:   cachedSessionId ?? undefined,
    login_status: "logged_in"
    // hashed_uid intentionally omitted — not yet available
  });

  // Step 2-3: wait for hashed_uid in background, max 10s
  try {
    const hashedUid = await Promise.race([
      hashedUidPromise,
      new Promise((_, reject) => setTimeout(() => reject(new Error('timeout')), 10000))
    ]);

    if (hashedUid) {
      sessionStorage.setItem('hashed_uid', hashedUid);

      // Step 3: push supplemental event with complete payload
      dataLayer.push({
        event:        "login",
        anonymous_id: cachedClientId  ?? undefined, // ← same IDs as Step 1
        session_id:   cachedSessionId ?? undefined, // ← must be identical
        hashed_uid:   hashedUid,
        login_status: "logged_in"
      });
    }
  } catch (e) {
    console.warn('[Tracking] supplemental login event abandoned', e);
    // Step 5: silent abandon — stitching completes on next page load via session restore
  }
}
RuleDetail规范说明
IDs must matchSupplemental event must use the exact same anonymous_id and session_id as the initial login event — Backend uses these to match the two events补发事件必须使用与第一次 login event 完全相同的 anonymous_id 和 session_id，后端依此匹配两条事件
Backend dedupBackend must handle receiving two login events for the same session — the second (with hashed_uid) completes the stitching; the first is not discarded后端需处理同一 session 收到两条 login event 的情况——第二条（含 hashed_uid）完成 stitching，第一条不丢弃
Supplemental timeout10 seconds — longer than the initial 3s GA4 timeout, as login API is a critical business call with higher reliability expectation补发超时设为 10 秒，长于 GA4 的 3 秒超时，因为登录接口是核心业务接口，可靠性预期更高
No re-fetch of IDsanonymous_id and session_id must be the cached values from initialization — never re-fetched at supplemental push time补发时使用初始化时缓存的 IDs，绝不重新获取
Backend prerequisite：后端在收到不含 hashed_uid 的 login event 时，必须以 anonymous_id + session_id 为 key 暂存这条记录，等待后续补发。若 10 秒内未收到补发事件，该条记录通过下次页面加载的 tracking_initialized（含 hashed_uid）完成 stitching。这个处理逻辑需要在后端 identity stitching 模块中明确实现。

Frontend Implementation Guide 前端实现总览

本章节是前端工程师的单一实现入口。Tracking 体系跨越多份 PRD（006 / 008 / 009），但所有前端工作共享同一个初始化入口。阅读本章节后，无需同时翻阅其他文档即可完成前端实现。
核心原则：所有 tracking 初始化工作必须通过统一入口模块执行。不允许 008 或 009 各自独立初始化 GA4 ID——anonymous_id 和 session_id 只获取一次，由初始化模块持有，后续逻辑作为条件分支挂载其上。
13.1 Unified Initialization Sequence 统一初始化执行序列
以下是每次页面加载时前端的完整执行顺序，覆盖所有 tracking 场景。每一步标注了对应的来源 PRD。
PseudocodeFrontend Tracking — Unified Entry Point
async function initTracking() {

  // ─── STEP 1: Consent gate ───────────────────────────── PRD-TRK-006 §10
  if (!consentGranted()) return; // 用户未授权 Cookie → 停止所有 tracking

  // ─── STEP 2: Fetch GA4 IDs (once, shared by all PRDs) ── PRD-TRK-006 §5
  const [clientId, sessionId] = await Promise.all([
    getGA4ClientId(),   // anonymous_id = GA4 client_id，3s 超时
    getGA4SessionId()   // session_id = GA4 ga_session_id，3s 超时
  ]);
  // 超时时为 undefined，不生成 UUID 替代

  // ─── STEP 3: Read URL params ─────────────────────────── PRD-TRK-008 §5
  const maRef    = getURLParam('ma_ref');    // MA 消息链接 token（007/008）
  const aimaRef  = getURLParam('aima_ref'); // Aima 对话链接 token（009）

  // ─── STEP 4: Push tracking_initialized ──────────────── PRD-TRK-006 §4
  const hashedUid = getCurrentHashedUid(); // 已登录时从 session 获取
  dataLayer.push({
    event:        "tracking_initialized",
    anonymous_id: clientId  ?? undefined,
    session_id:   sessionId ?? undefined,
    ...(hashedUid && { hashed_uid: hashedUid }),
    login_status: hashedUid ? "logged_in" : "anonymous"
  });

  // ─── STEP 5: MA link identity resolution ─────────────── PRD-TRK-008 §5
  if (maRef) {
    await resolveMARef({ maRef, anonymous_id: clientId, session_id: sessionId });
    // resolve 成功后 push ma_identity_associated event（详见 PRD-TRK-008 §11）
  }

  // ─── STEP 6: Aima Widget init (widget 场景) ──────────── PRD-TRK-009 §9
  if (isAimaWidgetPage()) {
    initAimaWidget({
      runtime_source: "website_widget",
      ga_session_id:  sessionId,   // 复用 STEP 2 已获取的值，不重复请求
      ga_client_id:   clientId
    });
  }

  // ─── STEP 7: Login event（登录成功时触发，不在页面初始化中）
  //            见 PRD-TRK-006 §4.3 Flow 3 — 使用与 STEP 2 相同的 IDs

}
禁止事项： 008 的 resolve 逻辑和 009 的 Widget 初始化不得各自独立获取 GA4 client_id / session_id。两者必须复用 STEP 2 中已获取的值，避免时序竞争和重复异步请求。
StepAction来源 PRD说明
1Check Cookie consent006 §10所有 tracking 的前置门控，未授权直接退出
2Fetch GA4 client_id + session_id（并行，3s 超时）006 §5–6全局唯一获取，所有后续步骤共用
3Read ma_ref and aima_ref from URL008 §5 009 §7URL 参数读取，无则跳过对应步骤
4Push tracking_initialized to dataLayer006 §4每次页面加载必须推送，无论后续步骤结果如何
5If ma_ref → call resolve-ma-ref API008 §5–6条件执行；完成后推送 ma_identity_associated
6If Widget page → init Aima Widget with GA4 context009 §9传入已有 session/client ID，不重新获取
7On login success → push login event（独立触发）006 §4.3使用 STEP 2 缓存的 IDs，登录后不得重新获取
13.2 Token Reference — 三种 Token 区分 What frontend reads vs what it never touches
前端会在 URL 中看到三种 tracking token，职责截然不同。下表明确前端对每种 token 的处理方式。
Token出现位置前端职责前端禁止来源 PRD
anonymous_id GA4 内部（不在 URL） 通过 gtag('get', ..., 'client_id') 获取；推送进 dataLayer；传给 resolve API 自行生成 UUID 替代；登录后重新生成 006 §2
hashed_uid Login API response 从登录接口 response 读取；存入 sessionStorage；登录时推送进 dataLayer 自行计算 SHA-256；写入 localStorage；传给第三方平台 006 §2
ma_ref URL 参数 ?ma_ref= 读取 URL 参数；原样传给 resolve-ma-ref API；不做任何解析 解码 JWT；解析 payload；执行 identity 逻辑 007/008
aima_ref URL 参数 ?aima_ref= 读取 URL 参数；作为 GA4 event 参数随 recommendation_click 传出 解码 token；执行任何 identity 或 resolve 操作 009
ma_ref ≠ aima_ref ≠ hashed_uid — 三个 token 服务于不同系统，不可混用。ma_ref 是 MA 批量消息追踪（PRD-TRK-007/008）；aima_ref 是 Aima 对话消息追踪（PRD-TRK-009）；hashed_uid 是登录用户身份标识（本文档）。URL 中可能同时存在 ma_ref 或 aima_ref，但不会同时出现两者。

前端在整个 Tracking 体系中的所有职责汇总。每项职责对应唯一来源 PRD，无重叠，无遗漏。

给前端同学的一句话总结 你只需要实现一个统一的 initTracking() 入口函数。它负责：① consent 检查 → ② 一次性获取 GA4 IDs → ③ 推送 tracking_initialized → ④ 按条件分支处理 ma_ref（调 resolve API）和 aima_ref（传给 Widget）。登录事件单独处理。所有 token 只读取、只传递，不解析、不计算。
