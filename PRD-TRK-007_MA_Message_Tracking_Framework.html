Background 背景

为支持 MA Attribution、Flow Conversion Analysis、Node Performance Analysis 及完整用户行为链路，系统需要建立统一的 MA Message Tracking Framework。
核心问题 当前 MA 发送的 Email / WhatsApp 消息中，活动链接不携带任何 tracking context，导致无法将「消息发送 → 用户访问 → 转化」完整链路打通。业务用户手动拼接参数会造成数据污染，且无法保证 identity 安全。系统需要一套完全由系统自动管理的 tracking 机制。
Pain Point当前痛点
MA links carry no tracking contextMA 活动链接不携带任何 tracking 参数
No flow / node attribution无法分析哪个 Flow / Node 带来访问与转化
No identity association from MA linksMA 链接访问用户无法与系统 identity 关联
Manual parameter appending causes data pollution业务用户手动拼接参数导致数据污染

MA Link Structure 链接结构

All MA message links use a single opaque parameter ma_ref to carry the full tracking context.
URLMA Message Link — Standard Format
https://www.welovesupermom.com/campaign/123?ma_ref=abcxyz123
Business users only configure the landing page URL. The system appends ?ma_ref= automatically at send time. No manual parameter configuration is required or permitted.
5.1 Payload Structure
The internal payload signed into ma_ref contains the following fields. The payload is JWT HS256 signed — the token is opaque and tamper-proof.

5.3 ma_ref Signing Specification — JWT HS256
ma_ref is a JWT signed with HMAC-SHA256. The payload is not encrypted — it contains only opaque tokens and attribution IDs, none of which are raw user identity. Signing prevents forgery and tampering. This follows industry-standard practice for MA tracking tokens (Braze, Klaviyo, Iterable).
Why JWT HS256 and not AES encryption? The payload contains only an opaque UUID (identity_token) and attribution IDs — no raw uid, phone, or email. Even if decoded, the payload reveals nothing sensitive. Signing (HS256) is sufficient to prevent forgery and tampering, and is significantly simpler to implement and maintain than symmetric encryption.
PropertySpecification规范说明
AlgorithmJWT HS256 (HMAC-SHA256)签名算法：HMAC-SHA256
Signing secretServer-side environment variable — never hardcoded, never exposed to Frontend or GTM签名密钥存于服务端环境变量，不写入代码，不暴露给 Frontend 或 GTM
Payload fieldsidentity_token · ma_flow_id · ma_node_id · ma_channel · exp (expiry timestamp)payload 包含四个追踪字段 + exp 过期时间戳
exp fieldUnix timestamp = issued_at + 2592000 (30 days). Backend verifies exp directly — no Redis TTL needed for expiry check.exp = 签发时间 + 30 天（Unix 时间戳）。Backend 直接验证 exp，不依赖 Redis TTL 判断过期
VerificationBackend verifies signature on every resolve-ma-ref call. Invalid signature → reject immediately, return ma_ref_invalid: true. Expired token → return ma_ref_expired: true.每次 resolve 调用都验签。签名无效返回 invalid；token 过期返回 expired
Secret rotationOn secret rotation, previously issued tokens become invalid. Coordinate rotation timing to minimise user impact (e.g. rotate outside peak send windows).密钥轮换后历史 token 失效，需在非高峰期执行轮换
JWTma_ref — JWT HS256 structure
// Header (standard JWT header)
{
  "alg": "HS256",
  "typ": "JWT"
}

// Payload
{
  "identity_token": "a1B2c3D4e5F6g7H8",  // opaque UUID — no raw identity
  "ma_flow_id":      "FLOW_001",
  "ma_node_id":      "NODE_003",
  "ma_channel":      "email",
  "exp":             1750723200        // Unix timestamp — issued_at + 30 days
}

// Signature: HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)
// Final ma_ref = base64url(header).base64url(payload).signature
// Example: eyJhbGciOiJIUzI1NiJ9.eyJpZGVudGl0eV90b2tlbiI6Ii4uLiJ9.xK9mPqR2vL
Backendresolve-ma-ref — verification logic (pseudocode)
function resolveMARef(ma_ref):
  // Step 1: verify signature
  payload = JWT.verify(ma_ref, SECRET_KEY, algorithm="HS256")
  if verification fails:
    return { ma_ref_invalid: true }

  // Step 2: check expiry (exp field in payload)
  if payload.exp < now():
    return { ma_ref_expired: true }

  // Step 3: lookup identity from Redis using identity_token
  identity = Redis.GET("ma_token:" + payload.identity_token)
  if identity is null:
    return { ma_ref_invalid: true }  // token not found or Redis evicted

  // Step 4: proceed with identity association
  return {
    profile_id:   identity.profile_id,
    ma_flow_id:   payload.ma_flow_id,
    ma_node_id:   payload.ma_node_id,
    ma_channel:   payload.ma_channel
  }
exp vs Redis TTL: The JWT exp field handles expiry — Backend checks exp directly without querying Redis. Redis TTL on ma_token:{uuid} is set to 30 days as a cleanup mechanism only, not as the primary expiry gate. This keeps the expiry logic self-contained in the token itself.

6.2 Per-recipient Token Timing
Unlike WhatsApp templates (which are pre-submitted to Meta), Email links are processed at send time. Every recipient gets a unique token generated at the moment their email is dispatched.
核心原则 Email 没有 Meta 预审机制，ma_ref 在发送时实时生成和拼接。每个收件人对应一条独立的 Redis 记录，TTL 从写入时开始计算。模板创建阶段不生成任何 token。
PropertyDetail说明
Token generation timingAt send time — per recipient, per email dispatch. Not at template creation time.发送时实时生成，不在模板创建阶段生成
Token uniquenessOne token per recipient per send. 1,000 recipients = 1,000 unique tokens = 1,000 Redis writes.每个收件人生成独立 token，1000 个收件人 = 1000 次写入
TTL start point30-day TTL begins from the moment the token is written to Redis (i.e. send time), not from template creation time.TTL 30 天从 token 写入 Redis 的时刻开始计算（即发送时刻）
Template creationBusiness user saves Landing Page URL only. No token is generated, no ma_ref is appended at this stage.模板创建阶段只保存 Landing Page URL，不生成 token，不拼接 ma_ref
ma_ref in template previewTemplate preview in the UI shows the raw Landing Page URL without ma_ref. ma_ref only appears in the actual sent email.UI 模板预览显示原始 URL，不含 ma_ref；ma_ref 只出现在实际发出的邮件中
Resend / retryIf the same email is resent to the same recipient (e.g. retry on bounce), a new token is generated. The old token remains valid until its TTL expires.重发时生成新 token，旧 token 在 TTL 内仍然有效

Redis write volume — implementation decision required: For large batch sends, this produces N Redis write operations per send (N = recipient count). Sequential individual writes will not scale. Backend engineering should evaluate and select the appropriate write strategy based on expected send volume and infrastructure constraints. Options include Redis pipeline, multi-exec, or async queue-based writes — the choice of approach is delegated to Backend engineering.
ConstraintDetail约束说明
Write atomicityEach token write must be atomic — partial writes (token stored without TTL, or wrong payload) must not occur每条 token 写入必须是原子操作，不允许写入不完整的记录
TTL accuracyTTL must be set in the same operation as the value write — not as a separate EXPIRE command, to avoid race conditionsTTL 必须与 value 在同一操作中设置（使用 SET … EX），不允许分两步执行
Write failure handlingIf a token write fails, the corresponding email must not be sent with a broken ma_ref. Backend must define retry or skip behavior per failed write.token 写入失败时，对应邮件不得携带无效 ma_ref 发出，Backend 需定义失败处理策略
Implementation approachDelegated to Backend engineering — pipeline, multi-exec, async queue, or other strategies are all acceptable provided the above constraints are met具体实现方案由 Backend 工程师决定，满足上述约束即可

7.3 Variable Index Management
When business templates contain custom variables (in message body or Landing Page URL), the system must assign ma_ref to a non-conflicting index. This is handled entirely by the system — business users are never exposed to this logic.

7.3.1 Edge Cases — Variable Index
Edge CaseRuleExample说明
Non-consecutive indices ma_ref = max(all existing indices) + 1. Gap indices (e.g. {{2}} when business uses {{1}} and {{3}}) are NOT filled by the system. Business uses {{1}} {{3}} → max = 3 → ma_ref = {{4}} 序号不连续时，ma_ref 取最大序号 +1，不填补空缺序号。{{2}} 的空缺不由系统填补
Meta variable limit reached (10 variables) If business has already used 10 variables (Meta max), system must block template submission and return a validation error. Business must reduce variable count before submitting. Business uses {{1}}–{{10}} → system blocks submission → error: "Template exceeds Meta variable limit. Remove at least one variable to allow tracking parameter injection." 业务变量已达 Meta 上限 10 个时，系统阻止提交并提示错误，要求业务减少变量数量
Why not fill gap indices? Meta validates that all declared variable indices have corresponding sample values at submission. If the system fills {{2}} as a gap filler, it must also provide a sample — but the system has no context for what that variable represents. Assigning ma_ref = max + 1 avoids this problem entirely.
Meta variable limit enforcement: This validation must happen at the UI level (disable Save button + show inline error) AND at the Backend submission level (reject API call). Both layers are required — UI validation alone is not sufficient.
